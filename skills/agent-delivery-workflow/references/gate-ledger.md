## Gate ledger

**Gate ledger.** A gate only in run context dies with the seat. From the project's first gate, the ledger is `~/.agent-delivery/projects/<project-slug>/gates.md` beside the config; no seat writes rows by hand. `scripts/gate_row.py` appends every row, deriving the gate id and UTC timestamp, and resolving `<branch>@<exact head>` from the current checkout unless `--head <branch>@<full 40-hex commit SHA>` is supplied. Use `--head` whenever a row records a past head; a SHA different from the current `HEAD` is accepted only with `--record reconstruction`, except on a row whose kind `gate_row.KINDS` marks `timely_at_ancestor` and whose head is an ancestor of `HEAD` (work recorded as it lands at an earlier head), and it must resolve to a commit object. The resolved head supplies the row, review, and push fields. `--check` validates the whole ledger first, every row against its predecessors in one pass, then the latest row (with `--mailbox`, that row's open-gate mailbox header); after every append run `scripts/gate_row.py --check --ledger <path>` and name the row it checked. A failed check means some row is invalid or the `prev_hash` chain is broken, including a hand-written row, so redo it through `scripts/gate_row.py` rather than editing the ledger by hand; a ledger record the tool cannot read back is not delivered. If a merge deleted the branch named by `<branch>@<head>`, the row still re-derives from the stored commit object; preserve and cite the full SHA in prose, and fetch the object before checking if it is not present locally.

The script is the row's sole specification (invocation shape `templates/gate-row-invocation.txt`); inputs are decided by the seat, not derived. `--brief` is the one-line `Agent brief:` restatement ("Attribution"): required on a `words=human` or `words=selected` row, refused on any other, and like `--note` it rejects `|` and `"` and is capped. `--quote` is the terminal field for the seat's own text (the act a seat row records, or the refused command on a runtime-denial row), so a `|` in it is data, and stays empty on a Human-words row; if the refused command would trigger the refusal on a command line, `--quote-file <path>` carries the same text from a file written without that runtime. `--note` is the seat's words, rejects `|` and `"`, and is capped; narrative belongs in the workspace record. Append one row per runtime denial naming one command, never an aggregate. No backfill: append an unrecorded resolved gate with `--record reconstruction --head <branch>@<full 40-hex commit SHA>` and name the source in the note. A recorded verdict that does not stand — a review whose Reviewer broke the no-mutation contract — is voided, never edited: append `kind=correction --status recorded:correction --void <id>`, where `<id>` is an earlier `recorded:review-pass` review row not already voided; the note names the row that holds the verdict now.

The channel is metadata: it says whether the Human typed in this seat or the Supervisor relayed it, and whether the Human chose from a dialog, which records a selection (`gate_row.py --check` refuses a `:dialog` row unless it records the selection in both its words and a `recorded:` status). `words=human` and `status=resolved:instruction` are only for text the Human typed (`channel=...:typed`). A Human-words row's timestamp, `channel=` and `words=` are its source line, and its `--brief` is the request, whether typed, relayed, selected, or delegated ("Attribution"). The Lead writes the ledger. If its runtime refuses the script, that is a seat constraint, never a Human ruling: record a runtime-denial row naming the refused command and retry in the narrowest allowed shape, including `--quote-file` when command text is refused. After two denials of one command signature (same command and reason despite varying surface text), stop retrying, route `BLOCKED`, and append no more denial row for that signature. If no shape lands, state the exact row and ask; the Human may direct the Supervisor to append it as the Human's hands, running the script with the row's values, `--brief` included, and `--writer supervisor-as-hands` and recording the instruction in the notebook. Typist does not change the field: `timely` when appended as the gate resolves, otherwise `reconstruction`. The ledger is an append-only record, not a control plane: it carries gate identity and resolution only, resolves by appending a resolution line rather than rewriting or deleting, stays outside the product repository with the notebook, routing, and task queues, and may cite acceptance artifacts tracked in the product repository. State the open-gate set/count only from `scripts/gate_row.py --open-gates`, or do not state it; a `status=` grep or `note=` count is invalid.

## Review and push coverage

Every script gate here, `gate_row.py` included, is soft: it catches a seat's mistake and is not a security boundary; its hash chain links backwards only, so a truncated tail, or a ledger replaced by a fresh `G1`, is not detected. A Tier P self-check is recorded as `status=recorded:self-check` and a passing review verdict as `status=recorded:review-pass`, each carrying `review=<base>..<head>`, the exact commit range that verdict covers, and a failing one as `status=recorded:review-fail`. A push to a feature branch is a Lead act once every commit it carries is covered by some review-pass or self-check range — one review covers a delivery's own intra-run intermediates ("Quiesce and commit"), and a stack of separately-reviewed deliveries tiles the range with one review row each. The Lead makes that push only through `gate_row.py --kind push ... --push`, which checks the whole row first (the `--head` form, the range, the boundary and the coverage below) and refuses before anything leaves the machine; only then does it run the non-force `git push origin <head>:refs/heads/<branch>`, never to the product line `origin/HEAD` names, under `gate_row.PUSH_TIMEOUT_S`, or the `--push-seconds` limit (an integer, 1 to 1800) when given, which kills the push's process group, writes no row and releases the ledger lock when it passes, and append the `kind=push` row once the push has landed. The pre-push hook runs inside that limit, so the Lead sizes `--push-seconds` to the project's pre-push stage worst case, as with every bounded run. A PR opens only after that row is printed, so a refused push leaves no branch to open it on. `--boundary` declares the delivery's scope, one path per flag, and a push whose range touches a path outside it is refused on append and on `--check`.

The pushed `<branch>@<head>` is the checked-out branch at its HEAD commit, and `--push` refuses any other branch or commit, and `--record reconstruction`. `gate_row.py` refuses the row unless every commit in `<push-base>..<head>` is so covered, is already on `origin/HEAD` (landed through its own review and merge), or is a merge commit whose parents are covered or precede the range and whose tree equals their automatic merge; a merge that resolves a conflict or adds content needs its own review. `charter_render.py` drops the same landed commits and clean merges from a Reviewer's range and declared scope. The product line moves only by the Human's merge (merge-ready, then `GO` or the Human's answer, `delegation.md`, "Durable delegation"), by a merge under a `land` pre-authorization (`delegation.md`, "Land decision"), by the Lead's merge of a doc-only PR (`delegation.md`, "Durable delegation"), or by a direct push on the Human's words for that occasion ("Current-request instructions"). A push blocked by a seat-permission classifier or harness takes the OPEN gate shape in "Attribution". A `kind=review` row records its reviewed range through `--review-base` (the tip the reviewed delivery was cut from — the current product line, or the tip of the reviewed delivery below it in a stack), exactly as a push row records `--push-base`; its head is `HEAD` by default, or the resolved `--head <branch>@<full 40-hex commit SHA>` when recording a past head (timely for an ancestor of `HEAD`, as above). First-publication review coverage starts at zero and covers the root commit through the tip. If existing ranges do not cover that history, stage a fresh Reviewer from the zero base before opening the push gate. The gate asks the Human to create the repository and add its remote first.
