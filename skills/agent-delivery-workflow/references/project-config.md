# Project Config

A project may keep standing delivery preferences in a Human-owned config file:

```text
~/.agent-delivery/projects/<project-slug>/config.json
```

`<project-slug>` is `state_root.slug_for` of the checkout's repository root (its directory name, lowercased); the same checkout always resolves to the same directory, which is what lets the gate ledger and this config survive a seat restart. The same directory holds the project's gate ledger (`gates.md`, defined in `lead.md`, "Gates and ledger"). This file is shared and cited, not copied.

The config is the Lead's layer: the Lead reads it at the start of a delivery or review-only route, before staffing any agent; the Supervisor may read it to audit; a Peer never reads it and receives the applied values through its charter; the lightweight route does not read it. When present, apply it. When absent, do not silently fall back to defaults: stop and ask the Human whether to create one, offering the two outcomes — create it now (record the settings they give, or seed `templates/config.json` with the values this run would use and confirm them, then apply it) or proceed this run on workflow defaults — and act only on their answer. Record `Config: none` (in the intake record, or beside the review boundary on a review-only route) only after the Human declines a config. Never create the file or assume defaults without that answer.

## Format

One JSON object in the shape of `templates/config.json`. `scripts/project_config.py` owns the key set, the value shapes, the placeholders `--expand` substitutes, and the path rule for `runtime-state-paths` entries; `--check <path>` prints `ok: <path>` or one refusal line on stderr and exits 1. A refusal is a config gap the Lead takes to the Human, never a value it guesses or skips. `launch-profiles` maps an exact agent kind to its profile: `seat-argv` applies to Lead and Peer launches (shared Human-question tool denials belong there), `peer-argv` holds Peer-only controls, `peer-settings-json` is optional Peer settings, and Reviewer/Architect-only `runtime-state-paths` lists the absolute directories and files the kind itself writes at start and while running, which the write fence admits (`templates/reviewer-write-fence.sb`); a project's own needs, such as package-manager caches, stay out of it and enter a charter as that project's addition. Argv values are literal arrays and settings are JSON objects; `--expand` returns argv/data for the existing start path and starts no process. The check keys follow `lead.md`, "Light and heavy checks": `checks-light` holds claim-shaped light commands and how to scope a test run to the changed paths, `checks-heavy` holds claim-shaped heavy commands, and `ci` names the workflow path(s) that run the heavy checks and the trigger that runs them, or `none`. The `local-ops` key lists the exact named commands `lead.md`, "Local operations", allows after a landed merge; it is Human-owned like the rest of this config. A key's value is always the one in force: a temporary override rewrites the affected keys in place, with an entry in the `provenance` object giving its reason and the values to restore. `provenance` maps a config key name (or `file`, for a note about the whole file) to an array of strings; no seat or script reads a setting from it.

## Precedence and guards

- An explicit Human instruction in the current request overrides the config; the config overrides workflow defaults.
- The config may add stricter local preferences; it may not weaken this workflow's safety boundaries. A `lane-defaults` entry raises a lane floor and never lowers a lane below what the hard-gate classes (`lead.md`, "Intake") require. `always-gate` adds Human gates; no key removes one, authorizes an external write, or skips review. `local-ops` stays inside that guard as `lead.md`, "Local operations", states. `worker-cap` bounds how many Engineers share the tree at once; it never permits overlapping owned paths or an agent that commits. The `engineer-fallback` and `engineer-fallback-args` keys play for a died Engineer the role `reviewer-fallback` plays for a Reviewer: they pre-choose the kind and the pinned model the Lead restaffs on when the primary Engineer's model is cooling down or otherwise refused. A replacement Engineer only has to stay inside its owned paths, which the partition already enforces, so this pair may repeat `engineer-kind` and needs only a model that is actually reachable.
`*-args` own model/posture; no external authority. Reviewer fallback needs exact configured kind/args launchable by Lead. If absent, ask Human; never guess. If refused at trigger, route `human-started`, not fallback coverage. Keep same write fence. Effort tunes reasoning, never scope or review depth.
- The config and other Human-owned files outside the repository — a global tool config, an installed skill directory — are read-only during a run. The run writes such a file only when the current Human explicitly instructs it to record that setting, reports the external change plainly, and appends one ledger line for the external write; absent that instruction, the Lead does not write outside the repository.
- Record the applied keys, or `Config: none`, in the intake record, and pass applied staffing and validation values into the affected charters.
