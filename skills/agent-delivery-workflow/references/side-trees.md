# Side trees

Split from `lead.md`; read when its pointer there says. A quoted heading without a file name is in this file or, if absent here, in `lead.md`.

### Baseline tree

One narrow exception exists, on the Human's terms; a Lead may neither widen nor read it away. A **baseline tree** may be created to attribute a failure — to establish a lane already failed before this delivery touched it — as a temporary worktree or clone, detached at a published commit, never on the delivery's own head. It is read-only: nothing is edited, staged, committed, branched, or pushed in it. It is never acceptance evidence; acceptance evidence comes from the caller's checkout at the exact head and nowhere else, save a check the archive sandbox described next admits (still at that exact head), and the record says so positively. Every number derived in a baseline tree names the tree it came from. Record it among the run's resources at intake, with the published commit it is cut at, and remove it at closeout under the proof `closeout.md` names. A baseline tree asked for anything beyond attributing a failure has stopped being one.

### Archive sandbox

A second, narrower surface serves the two needs the caller's checkout cannot. The first is an acceptance check whose claim is *about a different runtime environment* — for example a check that must run against a clean, unconfigured environment to prove a claim about that environment, which cannot honestly run inside the caller's configured checkout. This is not a second working tree and takes no registered git worktree: extract the exact reviewed head into a throwaway directory with `git archive <sha> | tar -x -C <dir>`, which holds the tracked tree at that SHA and nothing untracked, carries no `.git`, and cannot be committed from — a strictly weaker surface than a worktree, so a registered worktree is never opened for this. The second is an acceptance check that writes files — a build, or a test run that leaves outputs or caches — which in the caller's checkout would mutate the shared tree; when such a check reads git metadata the archive does not carry, the sandbox is a local clone detached at the exact head (`git clone --no-checkout <checkout> <dir>`, then `git -C <dir> checkout --detach <sha>`), never committed, branched, or pushed from. A dependency directory the check needs but the archive omits (an installed-package directory) MAY be symlinked in and is named in the record. It is extracted once and never edited, the check's own outputs aside: a change the check would require is a finding, not a sandbox edit. Its terms match the baseline tree's — read-only, justified only by one of these two causes, provenance stating the sandbox path and the exact SHA archived, recorded among the run's resources at intake (a Reviewer's own copy lives under its temp root and is named in its report instead) and removed at closeout — but unlike the baseline tree it MAY carry acceptance evidence for the check that caused it, with the record naming it as that check's source. Whoever owns the acceptance step uses it (the Lead at Evidence, the Reviewer at Review); it is not an Engineer's workplace. A sandbox asked for anything beyond those acceptance checks at the reviewed head has stopped being one.
