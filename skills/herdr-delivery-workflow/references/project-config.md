# Project Config

A project may keep standing delivery preferences in a Human-owned config file:

```text
~/.herdr/projects/<project-slug>/config.json
```

`<project-slug>` is the basename of the checkout's repository root (`basename "$(git rev-parse --show-toplevel)"`), lowercased; the same checkout always resolves to the same directory, which is what lets the gate ledger and this config survive a pane restart. The same directory holds the project's gate ledger (`gates.md`, defined in `lead.md`, "Gates and ledger"). This file is shared and cited, not copied.

The config is the Lead's layer: the Lead reads it at the start of a delivery or review-only route, before staffing any agent; the Supervisor may read it to audit; a Peer never reads it and receives the applied values through its charter; the lightweight route does not read it. When present, apply it. When absent, do not silently fall back to defaults: stop and ask the Human whether to create one, offering the two outcomes — create it now (record the settings they give, or seed `templates/config.json` with the values this run would use and confirm them, then apply it) or proceed this run on workflow defaults — and act only on their answer. Record `Config: none` (in the intake record, or beside the review boundary on a review-only route) only after the Human declines a config. Never create the file or assume defaults without that answer.

## Format

One JSON object in the shape of `templates/config.json`; every key is optional. Types: `engineer-kind`, `reviewer-kind`, `engineer-fallback`, `reviewer-fallback` and `target-line` are strings; `engineer-args`, `reviewer-args`, `engineer-fallback-args` and `reviewer-fallback-args` are arrays of strings, the exact argv after `--`; `checks-light`, `checks-heavy`, `local-ops` and `always-gate` are arrays of strings; `ci` is an object `{"trigger": "none"|"pr"|"push", "workflows": [...]}`; `lane-defaults` is an object; `worker-cap` is an integer. The kind, fallback and `target-line` strings and the items of `checks-light`, `checks-heavy`, `local-ops` and `always-gate` are non-empty, `lane-defaults` keys are non-empty and its values are `tiny`, `normal` or `high-risk`, `worker-cap` is at least 1, and `ci.workflows` is empty exactly when `trigger` is `none`. The OPT-IN `local-ops` key is an array of exact named commands the Lead may run on the Human's checkout AFTER a landed merge, such as dev DB migrate/seed or a preview-server restart (the preview server runs in its own checkout following the landed line, not the canonical work tree — `lead.md`, "Ownership and topology"). Its commands are limited to dev/disposable data and never an external write. `local-ops` is Human-owned like the rest of this config. The check keys follow `lead.md`, "Light and heavy checks": `checks-light` holds claim-shaped light commands and how to scope a test run to the changed paths, `checks-heavy` holds claim-shaped heavy commands, and `ci` names the workflow path(s) in `workflows` and the `trigger`, `pr` or `push`, that run the heavy checks, or `none`. When the Lead reads the config it runs `scripts/project_config.py --check <path>`, which prints `ok: <path>` and exits 0, or prints one refusal line on stderr and exits 1 for an unknown key, a wrong type, a duplicate key or invalid JSON. A refusal is a config gap the Lead takes to the Human, never a value it guesses or skips. A key's value is always the one in force: a temporary override rewrites the affected keys in place, with an entry in the `provenance` object giving its reason and the values to restore. `provenance` maps a config key name (or `file`, for a note about the whole file) to an array of strings; no seat or script reads a setting from it.

## Precedence and guards

- An explicit Human instruction in the current request overrides the config; the config overrides workflow defaults.
- The config may add stricter local preferences; it may not weaken this workflow's safety boundaries. A `lane-defaults` entry raises a lane floor and never lowers a lane below what the hard-gate classes (`lead.md`, "Intake") require. `always-gate` adds Human gates; no key removes one, authorizes an external write, or skips review. `local-ops` is consistent with that guard: it authorizes only the named local, non-external-write commands after a landed merge; absent the key, the operation stays Human-owned. Each run appends one `kind=local-ops` ledger row. It NEVER authorizes, performs, or substitutes for an external write: push, PR mutation, merge, and deploy stay Human gates. `worker-cap` bounds how many Engineers share the tree at once; it never permits overlapping owned paths or an agent that commits. The `engineer-fallback` and `engineer-fallback-args` keys play for a died Engineer the role `reviewer-fallback` plays for a Reviewer: they pre-choose the kind and the pinned model the Lead restaffs on when the primary Engineer's model is cooling down or otherwise refused. A replacement Engineer only has to stay inside its owned paths, which the partition already enforces, so this pair may repeat `engineer-kind` and needs only a model that is actually reachable.
- `*-args` values decide a Peer's launch posture: the Lead passes the role's block verbatim and contiguous and never adds, drops or substitutes a model, permission-mode or tool-deny flag (`charters.md`, "Writing charters", "Permission posture"). They pre-arm routine command approval so agents do not stall on per-command prompts; they never authorize push, PR mutation, merge, deploy, or another external write. Absent args for a role, or args with no arming flag where the kind's `--help` shows one, are a gap the Lead takes to the Human, never a posture it picks; for `reviewer-args`/`reviewer-fallback-args` the Human adds a mode that withholds writes to the tree when the kind has one. A blanket permission skip recorded here is the Human's standing waiver for that kind: the Lead passes it because the key holds it and records the Peer's posture as `bypassed` residual risk. The pre-chosen Reviewer fallback must be a seat the Lead's own runtime can start; if that runtime refuses a blanket skip in `reviewer-fallback-args`, every fallback trigger becomes a `human-started` Human gate, so that choice is no fallback. Unless the Human names another fallback, use the primary Reviewer kind on a different model with the same posture arguments, under the same write fence. A model reasoning-effort flag also rides in `*-args` like model selection (claude/agy `--effort`, pi `--thinking`); it tunes per-turn reasoning depth ONLY and never authorizes narrowing scope, staffing, acceptance, or review depth — that no-duration/effort-cut boundary (`lead.md`, "Quality floor") is a separate axis. There is deliberately no first-class `effort` key: the per-kind flag names and value sets differ (pi names it `--thinking`; agy omits `xhigh`/`max`), so no uniform key is possible and the `*-args` passthrough carries it per-kind-correctly instead.
- The config and other Human-owned files outside the repository — a global tool config, an installed skill directory — are read-only during a run. The run writes such a file only when the current Human explicitly instructs it to record that setting, reports the external change plainly, and appends one ledger line for the external write; absent that instruction, the Lead does not write outside the repository.
- Record the applied keys, or `Config: none`, in the intake record, and pass applied staffing and validation values into the affected charters.
