# Writing charters

Read this before sending any charter. A Peer is one thin role: an independent agent assigned one bounded outcome inside the delivery's single checkout. The disposition decides what it is this time — an **Engineer** that writes inside owned paths, a **Reviewer** that gives a read-only verdict on one exact head, or an **Architect** that gives a read-only second opinion for a `COUNCIL_REQUEST`. There is no separate profile per disposition, and a Peer never manages other agents. The charter is the Lead's whole instrument for a Peer: everything the Peer needs is copied in, and it explicitly forbids the Peer from loading or invoking the herdr-delivery-workflow skill, by any mechanism, and from following its references or templates, and never points the Peer at this skill's references or the project config — those are the Lead's layer, and a Peer that loads this skill acquires a second, conflicting authority layer and can start orchestrating, exactly the boundary the charter holds. When a lens from `structural-misfit-policy.md` applies, the Lead copies the relevant lenses into the charter rather than citing the file.

**Invariants the charter states in its own words** (every disposition): works only inside the assigned repository, checkout, scope, and authority, preserving unrelated changes; runs no orchestration — no hidden workers, background jobs, detached commands, schedules, or watches, and no `herdr` command beyond the report-send block's prompt and failed-send notification. One exception, for an Engineer or Reviewer only: one command at a time, a check its charter names, may run as its runtime's own background task with a runtime task id, started through the runtime's background option or moved to the background by the runtime at its timeout. It is never detached (no `nohup`, `setsid`, `disown`, trailing `&`, scheduler, or process outside the runtime's tracking), is awaited through the runtime's completion notice, not a sleep or poll loop, and is stopped only by its own task id. The seat sends no report until it has ended, and the report names each such task's id, command, how it started (explicit or moved at the timeout), end state, and exit code; any other background job stays banned. Every charter carries, by value, the pattern-kill guard clause: Never kill a process by pattern (`pkill -f`, `killall`, `pgrep ... | xargs kill`); stop only a process whose pid or task id you started yourself. Other seats share the machine and their argv carries test-runner names, so a pattern match kills them. Subagent custody follows `lead.md`, "Ownership and topology"; the writer ban is absolute. The Peer treats the charter's plan, approach, and file list as a provisional map, forms its own judgment, and challenges the premise with evidence when the code contradicts it; never expands scope, lowers the recorded lane, or creates an external effect (push, PR mutation, merge, deploy, credentials, permissions) without explicit authority; verifies its own work proportionately but never accepts it — the Lead accepts, and a settled Peer is evidence, not acceptance; reports a durable write only after it has landed and been read back, and derives every count, file list, and exit code from the record at the time of writing, naming its source; ends every turn that produces a result with one report or protocol message, sent to the Lead by prompt.

**Charter fields** (every disposition): `Disposition: Engineer | Reviewer | Architect`; exact outcome and acceptance boundary; recorded intake `Lane`, `Reason`, `Owners`, `Plan`, `Validation`; governing repository contracts and instructions; target repository and product line; checkout path, branch, base, merge-base; the Lead's agent name (the only prompt target the Peer may use) and the report format; the durable-write and derived-count rule in the charter's own words; the prohibition on unrelated cleanup, scope expansion, orchestration, and external effects. Two parts carry different force: the boundary — disposition, owned paths or reviewed head, exclusions, lane, gates, prohibitions — is binding; the solution shape — plan reference, suggested approach, named files-to-change — is provisional, and the Lead must not embed a predetermined implementation or disguised conclusion, stating open questions as open. When evidence contradicts the charter, the Peer raises the matching protocol message instead of complying silently.

**Permission posture.** A Peer that stops at an approval dialog for `git diff` or the test command is the most common stall, and the Lead cannot answer it. The project config decides a Peer's posture, never the Lead. At `herdr agent start`, pass the role's configured `*-args` as one contiguous block after `--`, plus the exact-kind profile expansion from `project_config.py`; the generic fields are fixed by code and contain literal argv/data only. The Lead passes configured args unchanged. Human approval is required for tighter posture. `roster.py --drift` uses the same expansion. Record `posture=<value>` by classifying the configured args against the runtime's own `--help` at staffing, not memory, never by choosing. Missing role args or required arming controls are a config gap the Lead takes to the Human; it picks no posture.

- `allowlisted` — the args carry the kind's arming axis, so the seat's command allowlist or scoped mode runs the charter's commands without a dialog. For a Reviewer or Architect the args may add a mode that withholds tree writes: these are two axes, not one flag, because a mode that withholds tree writes arms no command, so a seat started under it alone still stops at its first `git rev-parse`. Record `allowlisted` for the arming axis only, and say which axes the args passed. The configured command allowlist or scoped mode must arm the charter's commands without changing permission semantics; a posture that refuses the report-send block is a config gap for the Human.
- `bypassed` — the args hold a blanket skip of every prompt. The Human set that key, and the posture is residual risk, never proof of read-only; the Lead reads the diff at quiesce because nothing else stood between it and the tree.
- `none` — the kind has no permission model and runs every tool without asking. Same residual risk, charter prohibitions, and diff reading as `bypassed`; the Human's consent is the config key that named the kind.
- `human-started: <arg>` — the Lead's own runtime refuses to pass a config flag, usually a blanket skip. The Lead does not silently downgrade to `prompting` and does not staff the seat itself: it states the exact `herdr agent start` line and records the request as a Human gate with its ledger line, so the notification is that gate's own; the Human then starts the seat (its hands may be the Supervisor's pane on an explicit per-occasion permission). A Human who declines resolves the gate like any other, and the scope is `BLOCKED` or restaffed on a kind this runtime can pass — never downgraded to `prompting`. Treat the seat exactly as `bypassed` from there.
- `prompting` — the kind asks before commands and its `--help` shows no arming flag, so the config args pass none. Every dialog this Peer raises is then a Human interaction the Lead routes; say so in the charter so the Peer treats a pause at a dialog as expected.

When an Engineer is restaffed because its primary model was refused (`lead.md`, "Lifecycle and reports"), or a Reviewer is started on its pre-chosen fallback kind, the Lead uses that fallback's configured args and matching kind profile in the same expansion, and records its posture exactly as for the primary; those fallback arguments arm the same commands and grant no new external effect.

A Peer loads the Human's user skills, plugins, hooks and prompt templates as usual; only herdr-delivery-workflow is blocked. The configured profile supplies isolation controls as literal argv or settings data. Preserve the report-send block and its failed-send handling (`templates/report-by-prompt.txt`), user skill/extension accounting, and session identity evidence. No posture pre-authorizes push, PR mutation, merge, deploy, credentials, or another external write, and no posture changes what the charter permits: the posture decides whether the runtime enforces the boundary or only the charter does.

**Write fence.** A Reviewer or Architect whose posture does not withhold tree writes while keeping a shell runs under the existing OS write fence, so its no-mutation contract is held by the runtime, not only by the charter. On macOS the Lead fills `templates/reviewer-write-fence.sb` into `<run-dir>/fence-<peer>.sb`: it denies every file write except the temp roots, `/dev`, the configured `runtime-state-dir`, and the seat's two report-send files with their Write-tool temp siblings (`<file>.tmp.<pid>.<hex>`). In the new pane, before `herdr agent start`, run `herdr pane run <pane> "cd <checkout> && exec sandbox-exec -f <run-dir>/fence-<peer>.sb /bin/zsh -i"`, then `herdr pane run <pane> "touch <checkout>/.fence-probe"` and read the pane: it must show `Operation not permitted`. `herdr agent start` then launches the kind inside that shell, and the kind and every command it runs inherit the fence. Record `fence=sandbox-exec(<.sb path>; probe <command> -> Operation not permitted)` beside `posture=`, or `fence=none(<reason>)` where no OS fence is available; `scripts/charter_lint.py` requires the profile file and recorded probe, and refuses `fence=none` without a reason or when the seat needs a fence and `sandbox-exec` is available. A start-up failure under the fence names a write the kind needs: add that path to the seat's profile and record it, never the checkout or anything else under `~/.herdr`, and never drop the fence. The fence cannot exec a setuid binary such as `/bin/ps` under any profile: the charter names each check that needs one and skips exactly those, and the Lead runs them unfenced. The fence does not bound the Docker daemon: a fenced charter that allows containers pins the exact `docker` commands and mounts, the staffing line records residual docker-daemon writes, and every bind mount comes from under `$HOME`, prepared by the Lead, because Colima shares only `$HOME` and a `/private/tmp` mount is empty in the container. An Engineer is never fenced; it writes its owned paths.

**Dialog posture.** No non-Supervisor seat may expose a direct Human-question tool. At staffing, inspect runtime help, active tool inventory, and loaded extensions. Record `dialog-tools=<names | none>`, `dialog-deny=<names/patterns | none>`, and `dialog-source=<evidence>` on its staffing line. Never infer coverage from similar names or flag examples.

- `dialog=denied` — approved args deny every inventoried tool by exact name or matching pattern.
- `dialog=absent` — verified inventory contains none.
- Any exposed, undenied tool makes that kind/profile ineligible; ask the Human to choose an enforcing runtime/profile before launch.

A dialog-deny changes no permission posture. The staffing linter accepts only `denied`/`absent`, requires these evidence fields, and checks recorded names against denies. It cannot prove inventory completeness; record the actual source.

**Report by prompt.** The Lead copies the block in `templates/report-by-prompt.txt` into every charter unchanged, substituting only `<run-dir>`, `<peer-name>`, and `<lead-name>`; that template is the one live copy of the block.

The report file is the full durable evidence record the Lead reads when the wake never arrives; the prompt is only the wake plus its bounded summary and file path. These two `herdr` commands are the only ones a Peer runs.

**Escalation shapes** (`REOPEN_REQUEST` uses `templates/reopen-request.txt`; the other three share `templates/peer-escalation.txt`): `REOPEN_REQUEST` when a foundation, dependency, lifecycle, API, ownership, or verification premise fails, or evidence increases blast radius, irreversibility, uncertainty, ownership impact, or proof weakness beyond the lane (it carries the old and proposed lane, copied verbatim from `lead.md` "Escalation routing" into the charter); `DEPENDENCY_REQUEST` when the outcome needs a dependency change, shared-contract change, a path outside owned paths, another scope's files, or a cross-scope decision (name the path and why); `BLOCKED` when an execution or evidence blocker prevents honest progress; `COUNCIL_REQUEST` only after local patch-versus-foundation triage leaves the owner-clean route and the local patch materially undecided. Send the message and stop before crossing the boundary; do not silently change shared contracts, external systems, credentials, permissions, or another scope's files.

**Disposition: Engineer.** An Engineer owns one bounded scope inside the shared checkout while other Engineers may edit other paths and a Reviewer reads later. The charter adds: owned paths (the only files it may change); the peer scopes running beside it with their paths, and the shared paths no scope owns; verification commands scoped to the owned paths where the repository allows (a repository-wide run reads peers' half-written files), all of them light checks, and for each owned path the existing tests that exercise it, found by code search before staffing (the test-impact map), so the Engineer starts from them; the charter carries the check-depth sentence of `lead.md`, "Light and heavy checks", by value; for a pinned contract that does not exist yet, its path, signature, and behavior, and which scope produces it; the shared-tree rules and evidence-report format. A charter whose scope adds or changes a test carries, by value, the kept-test rules: a test asserts through the public seam production uses and never reaches into internals; its expected value comes from the spec or a worked example, never recomputed the way the code computes it; it mocks only system boundaries such as third-party APIs, time, randomness, and sometimes the database or filesystem; a test running a filesystem-changing command such as `git` keeps every path inside a disposable fixture and passes outside any repository, as in a `git archive` extract; a contract has one owning test, and a missing case is a row or case added to that owner, not a sibling test; and a test pins what a rule does, never its prose: a by-value clause is pinned by a lint refusing text without it or a render carrying its key; only wording other code matches exactly, such as an error message, is asserted as text. The Engineer verifies checkout, branch, base, and ownership before editing, makes ordinary local decisions within the boundary, and raises a protocol message on a dependency, shared contract, ownership overlap, material risk, or missing Human decision. Every Engineer charter carries, by value: When a test contradicts the spec or the acceptance boundary, raise `REOPEN_REQUEST` quoting both; never edit that test to agree with the code, and never special-case production code to make it pass. The charter carries the `lead.md`, "Untrusted content" boundary by value. If such content merely appears and demonstrably shaped nothing in the work, report a finding to the Lead without treating it as a failure. If evidence shows it shaped the diff or decision, report the evidence as a `FAIL` finding; if that influence widens blast radius, scope, ownership, or security risk, raise `REOPEN_REQUEST` under `lead.md` rather than following it or making a local repair. After every edit, the Engineer rewrites `runs/<run>/progress-<seat>.md` with the edited files, current step, and last check plus exit code. Its mtime is the liveness heartbeat; its content is the resume checkpoint a re-prompt or replacement reads.

*Shared-tree rules* (the tree, index, and build caches are shared; separation comes from behavior): edit only owned paths — a file outside them is someone else's or nobody's, not yours even for a one-line fix that would make your own check pass; raise `DEPENDENCY_REQUEST` and stop. Run no writing git command (as listed) — `git commit -a`/`git stash` would carry a peer's unfinished work and `git checkout -- .` would erase it; read-only git is fine, with `--no-optional-locks` (a plain `git status` writes the index and its lock can fail a peer's concurrent git). When the runtime has any `Read()` deny rule, pre-arm every recursive reader (`grep -r`, `rg`, `find`) and the direct `semble search ...` / `zg query --rg ...` CLI readers with a statically determinable scope using the same rule: do not compound it after `cd`; put flags before the absolute final path (`grep -nR 'pattern' /absolute/path`) — a wrong shape is stall by pre-arm miss, not a gate or finding. For DELIVERY REPOSITORY code search, the charter carries the `lead.md`, "Repository guidance" preference by value. A code-searching Peer invokes those preferred CLIs directly from Bash under the shared-tree rules and falls back to `grep`/`rg`/`read` when unavailable. Run no repository-wide formatter, linter `--fix`, code generator, dependency install, or lockfile update — those write outside owned paths; scope a formatter to owned files, a repository-wide pass is a sequential slice. Treat your own check results as provisional (a test may have run against a peer's half-written file); prefer the scoped commands, and when a check cannot pass until a peer's pinned contract lands, report it blocked on that contract instead of iterating. Build against a pinned contract exactly as pinned: mock it in your own tests, and do not create a stub at the producer's path. Keep your own list of every file you create, modify, or delete, since git cannot tell your edit from a peer's to the same path. Leave no process running when you report.

*Execution:* keep it foreground and bounded; implement the smallest complete slice inside the owned paths, run the checks that exercise it, keep every change explainable and inside owned paths, do not commit; when the slice is done, report by prompt and stop editing until a new instruction arrives. When a local wrapper, fallback, retry loop, cache, adapter, or compatibility path begins to own lifecycle, authority, synchronization, failure, or proof semantics that belong to the foundation, apply the `structural-misfit-policy.md` lenses the charter carries: report the evidence and owner-clean alternative, do not silently expand the workaround.

*Evidence report* (`templates/engineer-report.txt`): the report file retains the complete evidence, including `Edited files`, porcelain, pasted script output, and grep; each check row names the full head and whether the shared tree was clean or dirty (dirty: paths), beside its command and real exit code. Paste every quoted value from the run in its row; label a value carried from an earlier report, round, or run with its source and originating head, and never present it as this run's evidence; rerun the command where possible. A quoted value with no run behind it, or an unlabelled copied value, is a finding: the Reviewer tests the claim by re-deriving it on the reviewed head. Each check row pastes the ran and skipped counts its command printed, and a check that did not run is a failed row (`lead.md`, "Light and heavy checks"). For each test added or changed for a behaviour change, the report has a red-proof row: the command run on the pre-change code with only that test applied, its non-zero exit code and the failure line, or `n/a: <reason>` when the change adds no behaviour, such as a pure refactor; for each new function, type or module, the report has a reuse-search row: the code search it ran before writing it (`semble` or `zg`, `lead.md`, "Repository guidance"), the query and the hits, and why no hit served; `Outside owned paths` is `none` unless something went wrong, in which case naming it is the point. `Edited files` comes from your own actions, not git — the Lead compares it with the porcelain for your paths, and a file there you did not claim is how a peer's stray write gets caught. The prompt carries only the verdict/outcome line, a bounded summary, and the report path. A report file missing either list is invalid and comes back. Recompute the report after every edit.

**Disposition: Reviewer.** A Reviewer gives an evidence-bound verdict on an exact head for review-only work and non-trivial deliveries. `templates/reviewer-charter.txt` is the charter's starting shape: it carries every clause below by value with `<snake_case>` fields to fill, and `scripts/charter_lint.py` stays the check. `scripts/charter_render.py` fills those fields from one Lead command line: the Lead gives the run dir, base, head, pane, lane and reason, acceptance boundary, validation, prior review, and each required check (`--check`, repeated, including the conditional check blocks below), and the script derives the rest from git, the commits' `Seat:`/`Model:` trailers, and `config.json`, then writes `charter-review-<head12>.md` in the run dir and prints its sha256. The independent-review contract is owned here: the Reviewer is a distinct agent instance from every Engineer and the Lead, reviews the exact head, and reruns the light acceptance checks its charter lists. Judgment claims cite sources, challenge counter-readings, name falsifiers; not automated proof. Those checks always include the `floor_guard.py` run of `lead.md` Delivery step 7 on the reviewed range; the Reviewer pastes the ran and skipped counts of each rerun beside the reported ones, and re-derives every red-proof row by applying only the added or changed test files to the base in its scratch clone and running that row's command, one targeted run and never a mutant run. When the head adds or changes a test, the charter carries the kept-test rules of *Disposition: Engineer* by value and the Reviewer judges each added or changed test against them, a breach being a finding; it also reruns one reuse-search row's search and confirms its hits. When the head changes production behaviour, the Lead copies this check block into the charter's required checks by value and adds no other check for it: grep the production diff for each input and expected value the head's tests use; check one input the tests do not use, its expected value argued from the spec or run once as a targeted light check; a production branch keyed to a test literal is a finding that fails the head; no input sweep, mutant run or whole-suite run. The Reviewer lists, against the plan, each of these the plan did not call for: new files; abstractions with one caller; config or flags that no caller varies; handling for states the types or callers make impossible; old paths kept beside new ones; comments that restate the code. Each one is a finding, and it fails the head only when it crosses the acceptance boundary, under the *Verdict* rule. Every Reviewer charter carries, by value, the check-depth sentence of `lead.md`, "Light and heavy checks"; the live-wake guard clause: Never run `mailbox.py --wake` against a real seat; exercise wake only with a patched subprocess or a nonexistent seat name (expect `agent_not_found`); the time limit: Run `date -u +%FT%TZ` at each Lead prompt and before each required check; three hours after the latest Lead prompt with no verdict, stop any check still running by its own task id, start no further check and send `BLOCKED (time limit)` as a message, not a verdict, naming each required check done, with its result, or not done. It also carries, by value, the OCR delegate step: run `ocr delegate preview --format json --repo <checkout> --from <base> --to <head>`, then `ocr delegate rule --format json --repo <checkout> <reviewable paths>`; review each reviewable file's diff against its rule group with your own judgment, and report an OCR coverage block (`total_files`, `reviewed_files`, `skipped_files` each with a reason, `coverage_rate`) and each finding's path, line, category, and severity. OCR only selects files and resolves rules: the files it excludes stay in your review scope, you apply no fix, and its findings are verdict evidence like any other. When the reviewed unit's base is the null OID, the range starts at a root commit that `--from` cannot name: preview the root with `--commit <root>` in place of `--from`/`--to` and, when the head is past the root, also `--from <root> --to <head>`; the union of both reviewable lists feeds `ocr delegate rule`, with no graft or replace ref. If the preview lists 0 reviewable paths, skip `ocr delegate rule` and report `no OCR input` with the preview's exclusions, not `BLOCKED`; every file is then reviewed by hand. Otherwise, if `ocr` is missing or a delegate command exits non-zero, return `BLOCKED`. The step is a CLI call, not a skill load; an allowlist posture arms `ocr delegate`. When the slice adds or changes a script, lint, or validator, the Reviewer exercises it through its real input path on real inputs: it runs each changed file under `scripts/` from its own seat shell with the exact doctrine-cited invocation — the empty non-tty stdin an agent's Bash gives, with no pipe — and pastes the output in the verdict; it confirms each such script's tests drive `main()`/the CLI input path and mock only the external boundary (the subprocess or file); it runs a gate-ledger reader or writer against a `gates.md` produced by `scripts/gate_row.py`, never hand-built rows; and it confirms before review that a doctrine-enforcing lint or validator was run against real governed-project charters or records, not only the run's own fixtures. For a slice whose diff touches a verification or harness file — any file one of the charter's acceptance checks reads or executes: a test, fixture, grader, lint or CI configuration, or acceptance script — that changed file is itself a first-class review target: the Reviewer reads its diff for a hardcoded expected output, a weakened or removed assertion, a narrowed selection set, or a silenced check, pastes what it found, and returns `FAIL` on tamper, because rerunning a check the head changed reproduces the tamper. The charter adds: the full implementation SHA; the implementation reports and acceptance boundary; the repository guidance files the intake named (root and nested `AGENTS.md` or `CLAUDE.md`), or `none` when the repository has none; the prior review for a repair head; validation claims and required checks; the checkout, workspace, and pane used; the mode, the Lead's kind and model in solo-Lead mode, the kind and model running the review, and the kind and model of every Engineer whose scope is in the head; the partition (each scope's owned paths) when the head came from a delivery run. The reviewed unit is the commit range from the charter's recorded base — the product-line tip the delivery was cut from, or the reviewed tip below it in a stack — to that head; the Lead records the review-pass with `--review-base` set to that same base, so a stacked push is checked against the `review=<base>..<head>` range the Reviewer saw (`lead.md`, "Gates and ledger").

*Frozen tree:* review runs in the single checkout, from the Reviewer's pane, after implementation stopped. An env-isolated acceptance check, and a check that writes files, run in the archive sandbox the charter names or the Reviewer's own scratch copy of that exact head (`lead.md`, "Archive sandbox"), never in a second checkout or the checkout, which the write fence also refuses; the Reviewer records the path and edits nothing in it. That is honest evidence only when the tree is frozen: every staffed Engineer idle, the Lead has committed every partitioned scope or its solo-Lead scope, `git rev-parse HEAD` equals the named SHA, and porcelain is empty apart from entries the Lead already explained. Record `HEAD` and porcelain before the review and again after it, and discard the verdict if either moved.

*Staffing record* (`templates/reviewer-staffing-record.txt`): run the review under the independent-review contract above. Record every agent's kind and model beside its name, pane, workspace, and owned paths or exact head (a review-only route never reads this file, so the roster is built here). Choose the Reviewer kind and its fallback before staffing and pin both to the same exact head, taking them from the project config unless the current request overrides. Before sending any charter with `herdr agent prompt <peer>`, the Lead runs `scripts/charter_lint.py --charter <charter-file> --lead <lead-name> --repo <checkout>` (`--staffing <record>` is required for an Engineer, Reviewer, or Architect charter; the script owns its other checks) and dispatches only after it exits 0. The `OK:` line labels SHA-256 digests of the exact charter and optional staffing-record bytes linted; the Lead copies that line into run evidence, never into the staffing record. The lint covers only the supplied files at dispatch: it does not revisit closed-run records, skip files, or walk directories, and a lint change owes no rewrite of them. Write the staffing record before the review starts. Each `posture=` value is a measurement taken while staffing that seat, never populated from an earlier record: an earlier refusal is not incapacity now, an earlier success not capability now. When the intended route is unchanged, the required current `herdr agent start` is the measurement; when an earlier result would instead push the Lead to `human-started`, `prompting`, or FALLBACK without attempting the configured posture, the Lead first attempts that posture for the current seat and writes the argument attempted and the current pass or refusal beside that seat's `posture=` line. The record's FALLBACK trigger list is fixed text — copy it verbatim, because it states when a substitution fires, not what happened this run. Name the Reviewer after the head it reviews with an abbreviated SHA that fits the agent name rule — `review-<first 12 hex of the SHA>` — so the listing alone proves which head a verdict covers. One Reviewer instance reviews one head: a new head, a repair head included, gets a new instance under that head's name, started after the previous Reviewer is retired by `herdr-cli.md`, "Tear down an agent", with its report and transcript kept. A Reviewer is never renamed onto a new head or re-prompted with one, because a reused seat carries its earlier reasoning and reports into the next verdict. A replacement for a verdict that does not stand (a FALLBACK trigger, or a review row voided by a `kind=correction` row) reviews that head as a first review: its charter says `Prior review: none` and points at no artifact of the voided verdict — not its report, send file or transcript, nor a ledger range or whole-ledger read that holds that verdict's rows or their correction; a ledger row it needs is quoted in the charter by exact id. A Reviewer posture of `bypassed` or `none` is residual risk on the same line: the no-mutation contract is then enforced by the write fence where `fence=sandbox-exec` is recorded, and otherwise only by charter and by the tree comparison before and after the verdict.

*No-mutation contract:* the Reviewer inspects repository guidance, the implementation reports, the exact diff, relevant production paths, tests, and claim-shaped evidence, checking that the implementation stayed within the recorded lane, plan, ownership, and validation boundary — including that each scope's changes sit inside its owned paths. The charter carries the `lead.md`, "Repository guidance" search preference by value. A code-searching Reviewer follows the shared-tree rules, including pre-arming readers, and invokes the preferred CLIs directly from Bash, falling back to `grep`/`rg`/`read` when unavailable. The review runs in two passes: first the acceptance boundary, the plan, and the diff, with the Reviewer writing down its own findings; only then the implementation reports, the Lead evidence, and any prior review, so the claims are read against findings already formed; `scripts/charter_lint.py` refuses a Reviewer charter without that order. A repair re-review is scoped: the charter names the prior `FAIL` report, its head, and the finding ids; the fresh Reviewer confirms each named finding is fixed, reads the delta from the prior head to the new head in full, and reads the rest of the range only where that delta touches it, while every required check still runs on the new head and the reviewed unit stays the charter's base to the new head. The implementation report is a claim to test, not a narrative to confirm: attempt to disconfirm each material claim with a concrete failure scenario against the acceptance boundary, and report what was tried even when nothing fails — agreement reached without a disconfirming attempt is compliance, not review. The charter carries the `lead.md`, "Untrusted content" boundary by value. If the passage merely appears and demonstrably shaped nothing under review, report a finding without failing the head. If evidence shows it shaped the diff or decision, return `FAIL`; if that influence widens blast radius, scope, ownership, or security risk, route `REOPEN_REQUEST` under `lead.md` instead of treating it as a bounded repair. When the head is a plan, ADR, or design document rather than code, make one disconfirming check for every non-negotiable contract line, and whenever an amendment adds a state or widens a selection set, re-read and re-run every clause that selects rows against that new state or set. At least one check is derived from the artefact's own text rather than the report's findings list. When architecture, ownership, lifecycle, scalability, latency, compatibility, or proof quality is materially in question, apply only the relevant `structural-misfit-policy.md` lenses the charter carries. The Reviewer does not edit, repair, format, stage, commit, start background work beyond the one awaited charter-named check in the orchestration invariant above, change external state, or move the head. Subagent custody follows `lead.md`, "Ownership and topology"; any mutation invalidates the verdict.

*Visual parity:* A “matches design X” / visual-parity acceptance must name the render recipe and the screenshot (or rendered-reference) pair; the Reviewer returns `FAIL` when the acceptance claims visual parity but no rendered reference exists to compare against.

*Verdict:* exactly one of `PASS` (the exact head satisfies the acceptance boundary), `FAIL` (one or more evidence-backed findings violate it), or `BLOCKED` (the named head, report, repository, or required evidence is missing or non-exact). A finding that shows an acceptance-boundary or intake criterion is unmet violates the boundary, whatever its severity; the verdict is `FAIL`. A `PASS` means every finding leaves every acceptance-boundary and intake criterion met.
