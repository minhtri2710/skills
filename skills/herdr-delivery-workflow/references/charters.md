# Writing charters

Read this before sending any charter. A Peer is one thin role: an independent agent assigned one bounded outcome inside the delivery's single checkout. The disposition decides what it is this time — an **Engineer** that writes inside owned paths, a **Reviewer** that gives a read-only verdict on one exact head, or an **Architect** that gives a read-only second opinion for a `COUNCIL_REQUEST`. There is no separate profile per disposition, and a Peer never manages other agents. The charter is the Lead's whole instrument for a Peer: everything the Peer needs is copied in, and it explicitly forbids the Peer from loading any skill, plugin, or skill file by any mechanism at any point, and never points the Peer at this skill's references or the project config — those are the Lead's layer, and a Peer that loads a workflow skill acquires a second, conflicting authority layer and can start orchestrating, exactly the boundary the charter holds. When a lens from `structural-misfit-policy.md` applies, the Lead copies the relevant lenses into the charter rather than citing the file.

**Invariants the charter states in its own words** (every disposition): works only inside the assigned repository, checkout, scope, and authority, preserving unrelated changes; runs no orchestration — no subagents, hidden workers, detached commands, background jobs, schedules, or watches, and no `herdr` command beyond the report-send block's prompt and failed-send notification; treats the charter's plan, approach, and file list as a provisional map, forms its own judgment, and challenges the premise with evidence when the code contradicts it; never expands scope, lowers the recorded lane, or creates an external effect (push, PR mutation, merge, deploy, credentials, permissions) without explicit authority; verifies its own work proportionately but never accepts it — the Lead accepts, and a settled Peer is evidence, not acceptance; reports a durable write only after it has landed and been read back, and derives every count, file list, and exit code from the record at the time of writing, naming its source; ends every turn that produces a result with one report or protocol message, sent to the Lead by prompt.

**Charter fields** (every disposition): `Disposition: Engineer | Reviewer | Architect`; exact outcome and acceptance boundary; recorded intake `Lane`, `Reason`, `Owners`, `Plan`, `Validation`; governing repository contracts and instructions; target repository and product line; checkout path, branch, base, merge-base; the Lead's agent name (the only prompt target the Peer may use) and the report format; the durable-write and derived-count rule in the charter's own words; the prohibition on unrelated cleanup, scope expansion, orchestration, and external effects. Two parts carry different force: the boundary — disposition, owned paths or reviewed head, exclusions, lane, gates, prohibitions — is binding; the solution shape — plan reference, suggested approach, named files-to-change — is provisional, and the Lead must not embed a predetermined implementation or disguised conclusion, stating open questions as open. When evidence contradicts the charter, the Peer raises the matching protocol message instead of complying silently.

**Permission posture.** A Peer that stops at an approval dialog for `git diff` or the test command is the most common stall, and the Lead cannot answer it. Set the posture once per seat at `herdr agent start`, through the kind's native arguments after `--`, recorded beside the seat and kind. Learn the flags from the kind's own `--help` at staffing, not memory; the help settles whether the kind has a command allowlist, a scoped mode, or both. The project config supplies argument values (`engineer-args`, `engineer-fallback-args`, `reviewer-args`, `reviewer-fallback-args`) when present but never answers what the kind offers, and silence there about a kind is not evidence it offers nothing finer. Choose the finest posture the kind offers, recorded as `posture=<value>`:

- `allowlisted` — the kind accepts a command allowlist: pre-authorize exactly the read-only and verify commands the charter names plus the two `herdr` commands in the report-send block, and for a Reviewer or Architect add a mode that withholds tree writes when the kind has one. These are two axes, not one flag: a mode that withholds tree writes arms no command, so a seat started under it alone still stops at its first `git rev-parse`. Record `allowlisted` for the arming axis only, and say which axes were passed.
- `bypassed` — the kind offers only a blanket skip of every prompt. Pass it only when the project config records it for this kind; the key is the Human's standing waiver, and the posture is residual risk, never proof of read-only. The charter forbids subagents, background work, and every external write in words, and the Lead reads the diff at quiesce because nothing else stood between it and the tree.
- `none` — the kind has no permission model and runs every tool without asking. Same residual risk, charter prohibitions, and diff reading as `bypassed`; the waiver is the config key that named the kind.
- `human-started: <arg>` — the config records a blanket skip for a kind that offers nothing finer, and the Lead's own runtime refuses to pass it. The Lead does not silently downgrade to `prompting` and does not staff the seat itself: it states the exact `herdr agent start` line and records the request as a Human gate with its ledger line, so the notification is that gate's own; the Human then starts the seat (its hands may be the Supervisor's pane on an explicit per-occasion permission). A Human who declines resolves the gate like any other, and the scope is `BLOCKED` or restaffed on a kind this runtime can pass — never downgraded to `prompting`. Treat the seat exactly as `bypassed` from there.
- `prompting` — no argument was passed, because the config records none and the kind's `--help` showed no allowlist and no scoped mode, or because the Lead's own runtime refused to pass the arguments and the `human-started` case does not apply. Start the Peer anyway and record which: a refusal from the Lead's harness is a fact about its permissions, not a Human ruling. Every dialog this Peer raises is then a Human interaction the Lead routes; say so in the charter so the Peer treats a pause at a dialog as expected.

When an Engineer is restaffed because its primary model was refused (`lead.md`, the roster-reconcile rules), the Lead starts the replacement with `engineer-fallback-args` in place of `engineer-args` and records its posture exactly as for the primary; those fallback arguments arm the same commands and grant no new external effect.

Where the kind offers native disable flags for skill loading or extensions, pass them at staffing alongside the posture (for `pi`, `--no-skills` and `--no-extensions`). After start, read the pane status line once and record `extensions=<none | name(s)>` beside the seat: the invariant is accounted, not necessarily absent, so a named, allowed extension is acceptable and an unrecorded extension is the defect. No posture pre-authorizes push, PR mutation, merge, deploy, credentials, or another external write, and no posture changes what the charter permits: the posture decides whether the runtime enforces the boundary or only the charter does.

**Dialog posture.** Every delivery seat except the Supervisor also carries a dialog posture, recorded as `dialog=` beside `posture=` and set the same way — from the kind's own `--help` and tool list at staffing, never memory or a baked-in table. A coding-agent kind may expose a tool that opens a blocking user-question dialog, which blocks the seat from the Supervisor's prompt channel and leaves the pane readable only to its viewport, so no delivery seat but the Supervisor may keep it:

- `dialog=denied` — the kind offers a native deny: pass it at staffing. Required wherever a deny exists. Learn the exact flag from `--help`; two shapes seen are a tool-deny list (`claude`, `-- --disallowedTools AskUserQuestion`; `pi`, `-- --exclude-tools ask_question`) and a per-invocation toolset allowlist passed without the question toolset.
- `dialog=absent` — the kind's `--help` and tool list show no user-question tool; record it as checked.
- `dialog=residual` — the kind has the tool and offers no deny (`agy` today, whose `ask_user` is built in). Announce it to the Human once at staffing as a pre-arm miss, record `dialog=residual`, and put the no-dialog prohibition in the charter in words (a Peer routes a fork to the Lead, never the Human).

A dialog-deny is not a permission posture: it arms no command and changes no `posture=` value; record the two dimensions separately. The Supervisor is the one seat started with its user-question tool intact.

**Report by prompt.** The Lead copies the following block into every charter unchanged, substituting only `<run-dir>`, `<peer-name>`, and `<lead-name>`:

- Write the finished report/verdict to `<run-dir>/report-<peer-name>.md` with the editor/write tool (never via the shell), then print it as the pane's final output.
- At send time, compose a prompt containing the verdict/outcome line, a bounded summary of no more than roughly 200 words, and `full report at <run-dir>/report-<peer-name>.md`; send only that composed prompt with `herdr agent prompt <lead-name> ...` (no `--wait`). Do not send the report file contents.
- If that command exits non-zero: `herdr notification show "<peer-name>: report send failed" --body "<run-dir>/report-<peer-name>.md" --sound request`, then stop. Do not retry the send in either case.

The report file is the full durable evidence record the Lead reads when the wake never arrives; the prompt is only the wake plus its bounded summary and file path. These two `herdr` commands are the only ones a Peer runs.

**Escalation shapes** (`templates/peer-escalation.txt`): `REOPEN_REQUEST` when a foundation, dependency, lifecycle, API, ownership, or verification premise fails, or evidence increases blast radius, irreversibility, uncertainty, ownership impact, or proof weakness beyond the lane (it carries the old and proposed lane, copied verbatim from `lead.md` "Escalation routing" into the charter); `DEPENDENCY_REQUEST` when the outcome needs a dependency change, shared-contract change, a path outside owned paths, another scope's files, or a cross-scope decision (name the path and why); `BLOCKED` when an execution or evidence blocker prevents honest progress; `COUNCIL_REQUEST` only after local patch-versus-foundation triage leaves the owner-clean route and the local patch materially undecided. Send the message and stop before crossing the boundary; do not silently change shared contracts, external systems, credentials, permissions, or another scope's files.

**Disposition: Engineer.** An Engineer owns one bounded scope inside the shared checkout while other Engineers may edit other paths and a Reviewer reads later. The charter adds: owned paths (the only files it may change); the peer scopes running beside it with their paths, and the shared paths no scope owns; verification commands scoped to the owned paths where the repository allows (a repository-wide run reads peers' half-written files); for a pinned contract that does not exist yet, its path, signature, and behavior, and which scope produces it; the shared-tree rules and evidence-report format. The Engineer verifies checkout, branch, base, and ownership before editing, makes ordinary local decisions within the boundary, and raises a protocol message on a dependency, shared contract, ownership overlap, material risk, or missing Human decision.

*Shared-tree rules* (the tree, index, and build caches are shared; separation comes from behavior): edit only owned paths — a file outside them is someone else's or nobody's, not yours even for a one-line fix that would make your own check pass; raise `DEPENDENCY_REQUEST` and stop. Run no writing git command (as listed) — `git commit -a`/`git stash` would carry a peer's unfinished work and `git checkout -- .` would erase it; read-only git is fine, with `--no-optional-locks` (a plain `git status` writes the index and its lock can fail a peer's concurrent git). When the runtime has any `Read()` deny rule, pre-arm every recursive reader (`grep -r`, `rg`, `find`) with a statically determinable scope: do not compound it after `cd`; put flags before the absolute final path (`grep -nR 'pattern' /absolute/path`) — a wrong shape is stall by pre-arm miss, not a gate or finding. Run no repository-wide formatter, linter `--fix`, code generator, dependency install, or lockfile update — those write outside owned paths; scope a formatter to owned files, a repository-wide pass is a sequential slice. Treat your own check results as provisional (a test may have run against a peer's half-written file); prefer the scoped commands, and when a check cannot pass until a peer's pinned contract lands, report it blocked on that contract instead of iterating. Build against a pinned contract exactly as pinned: mock it in your own tests, and do not create a stub at the producer's path. Keep your own list of every file you create, modify, or delete, since git cannot tell your edit from a peer's to the same path. Leave no process running when you report.

*Execution:* keep it foreground and bounded; implement the smallest complete slice inside the owned paths, run the checks that exercise it, keep every change explainable and inside owned paths, do not commit; when the slice is done, report by prompt and stop editing until a new instruction arrives. When a local wrapper, fallback, retry loop, cache, adapter, or compatibility path begins to own lifecycle, authority, synchronization, failure, or proof semantics that belong to the foundation, apply the `structural-misfit-policy.md` lenses the charter carries: report the evidence and owner-clean alternative, do not silently expand the workaround.

*Evidence report* (`templates/engineer-report.txt`): the report file retains the complete evidence, including `Edited files`, porcelain, pasted script output, and grep; every check has its real exit code and the note that it ran on the shared tree; a skipped check has its reason; `Outside owned paths` is `none` unless something went wrong, in which case naming it is the point. `Edited files` comes from your own actions, not git — the Lead compares it with the porcelain for your paths, and a file there you did not claim is how a peer's stray write gets caught. The prompt carries only the verdict/outcome line, a bounded summary, and the report path. A report file missing either list is invalid and comes back. Recompute the report after every edit.

**Disposition: Reviewer.** A Reviewer gives an evidence-bound verdict on one exact implementation head — for review-only work and every non-trivial delivery review. A Reviewer charter for a script that reads or writes the gate ledger must exercise it against a `gates.md` produced by `scripts/gate_row.py`, never hand-built rows, because those can miss the real format. For any slice that adds or changes a file under `scripts/`, the Reviewer runs each changed script from its own seat shell with the exact doctrine-cited invocation — the empty non-tty stdin an agent's Bash gives, with no pipe — and pastes the output in the verdict, because a green test suite that exercises only the pure function misses a broken input path. It also confirms that each such script's tests drive `main()`/the CLI input path and mock only the external boundary (the subprocess or file), not merely the pure formatter. The charter adds: the full implementation SHA; the implementation reports and acceptance boundary; validation claims and required checks; the checkout, workspace, and pane used; the mode, the Lead's kind and model in solo-Lead mode, the kind and model running the review, and the kind and model of every Engineer whose scope is in the head; the partition (each scope's owned paths) when the head came from a delivery run.

*Frozen tree:* review runs in the single checkout, from the Reviewer's pane, after implementation stopped. That is honest evidence only when the tree is frozen: every staffed Engineer idle, the Lead has committed every partitioned scope or its solo-Lead scope, `git rev-parse HEAD` equals the named SHA, and porcelain is empty apart from entries the Lead already explained. Record `HEAD` and porcelain before the review and again after it, and discard the verdict if either moved. A review taken while any Engineer is still editing is not evidence, however clean the diff looked.

*Staffing record* (`templates/reviewer-staffing-record.txt`): run the review on a kind differing from every Engineer's when another kind is installed; in solo-Lead mode on a kind and model both differing from the Lead. Record every agent's kind and model beside its name, pane, workspace, and owned paths or exact head (a review-only route never reads this file, so the roster is built here). Choose the Reviewer kind and its fallback before staffing and pin both to the same exact head, taking them from the project config unless the current request overrides. Write the staffing record before the review starts. Each `posture=` value is a measurement taken while staffing that seat, never populated from an earlier record: an earlier refusal is not incapacity now, an earlier success not capability now. When the intended route is unchanged, the required current `herdr agent start` is the measurement; when an earlier result would instead push the Lead to `human-started`, `prompting`, or FALLBACK without attempting the configured posture, the Lead first attempts that posture for the current seat and writes the argument attempted and the current pass or refusal beside that seat's `posture=` line. The record's FALLBACK trigger list and INDEPENDENCE rule are fixed text — copy them verbatim whatever the scenario, because they state when a substitution fires and what a same-kind review would mean, not what happened this run; deciding the fallback in advance is what keeps a substitution visible. Name the Reviewer after the head it reviews with an abbreviated SHA that fits the agent name rule — `review-<first 12 hex of the SHA>` — and rename it with `herdr agent rename` whenever that head changes, so the listing alone proves which head a verdict covers; a name pointing at a head the Reviewer no longer sits on is worse than no name. A Reviewer posture of `bypassed` or `none` is residual risk on the same line: the no-mutation contract is then enforced only by charter and by the tree comparison before and after the verdict.

*No-mutation contract:* the Reviewer inspects repository guidance, the implementation reports, the exact diff, relevant production paths, tests, and claim-shaped evidence, checking that the implementation stayed within the recorded lane, plan, ownership, and validation boundary — including that each scope's changes sit inside its owned paths, since a stray file is a partition breach the diff shows. The implementation report is a claim to test, not a narrative to confirm: attempt to disconfirm each material claim with a concrete failure scenario against the acceptance boundary, and report what was tried even when nothing fails — agreement reached without a disconfirming attempt is compliance, not review. When the head is a plan, ADR, or design document rather than code, make one disconfirming check for every non-negotiable contract line, and whenever an amendment adds a state or widens a selection set, re-read and re-run every clause that selects rows against that new state or set. At least one check is derived from the artefact's own text rather than the report's findings list. When architecture, ownership, lifecycle, scalability, latency, compatibility, or proof quality is materially in question, apply only the relevant `structural-misfit-policy.md` lenses the charter carries. The Reviewer does not edit, repair, format, stage, commit, launch subagents, start background work, change external state, or move the head. If the runtime boundary cannot prove read-only execution, record that as residual risk; the Lead still compares the tree before and after, and any mutation invalidates the verdict.

*Verdict:* exactly one of `PASS` (the exact head satisfies the acceptance boundary), `FAIL` (one or more evidence-backed findings violate it), or `BLOCKED` (the named head, report, repository, or required evidence is missing or non-exact). The report file retains the full evidence, including file/line evidence, Edited files, porcelain, pasted script output, grep, commands and results, residual risks, and the exact reviewed SHA; a verdict applies only to the named SHA. The prompt carries the verdict/outcome line, a bounded summary, and the report path. After the verdict, recompute `HEAD` and porcelain and discard the verdict if either changed. Send it to the Lead by prompt like any report. A `FAIL` is routed by the Lead (`lead.md` "Routing review findings"); the Reviewer never repairs source or assigns a solo-Lead repair, and a finding that increases scope, architecture, ownership, or proof risk returns `REOPEN_REQUEST`. Every fix creates a new exact head and requires a new review.

**Disposition: Architect.** The read-only second-opinion seat a `COUNCIL_REQUEST` may open (`structural-misfit-policy.md` decides whether one is worth spending). The charter adds the exact head or recorded quiesce state, the competing routes, and the specific question, and staffs it on a kind differing from every Engineer's when available, with read-only access, no mutation, no subagents, no background work. The seat is sealed: the Architect does not inspect another council seat's report, the Engineers' panes, or the Lead's ruling before submitting. It returns one evidence-bound `Assessment` (observations, unsafe assumptions, alternatives, recommendation, strongest counterargument, reversal conditions) by prompt to the Lead and stops. The Lead retains the ruling; an Architect recommends and never accepts, edits, or routes work.
