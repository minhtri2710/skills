# Closeout

## Acceptance custody

Before review, recompute the implementation repository's full `git rev-parse HEAD`, merge-base, changed-file list, `git --no-optional-locks status --porcelain --untracked-files=all`, and every acceptance command and real exit code. A moving branch, missing commit, stale report, unexplained dirty state, or a staffed Engineer still working is not reviewable: return it to the owning Engineer in partitioned mode, repair the declared scope in solo-Lead mode, or route the blocker. Accept only after an independent Reviewer returns `PASS` for that exact head and the Lead confirms the checkout did not move or become dirty during the review; any implementation change after review creates a new head and requires a fresh review. Preserve one verification ledger for the whole run (`templates/ledger.txt`), repeating the `HEAD` section for every head — the candidate, each repair head, the reviewed head, the integrated head — so each carries its own fresh evidence and verdict. A head with no `Verdict` line has not been reviewed; a repair head that inherits the section above it has not been evidenced. A later green result never silently replaces unreconciled evidence: state what changed and why the earlier failure is resolved. `repair-<n>` numbers the repair cycles from 1 and is a count, not a permission: it does not raise `repair-cap`, and reaching the cap ends the loop. A repair head numbered above the cap is written only after the Human authorized that cycle, and the gate ledger is where that authorization is recorded.

**Acceptance and cleanup.** Before final acceptance, preserve the implementation report, exact reviewed head, Reviewer verdict, integrated head when integration happened, changed files, check results on both the reviewed and integrated head, skipped-check reasons, a causal classification of every failure, residual risks, and next action. For a slice shipping or changing a doctrine-enforcing lint/validator, acceptance custody preserves as evidence the output of running that lint against the real apex and munsu live records. Acceptance requires claim-shaped checks plus `PASS` for the same exact head; a later green result does not replace an unreconciled earlier failure. On a run that passed independent review and landed (merged, or vacuously-green where there is no CI), the Lead writes one lesson record per genuine lesson learned into `~/.herdr/projects/<project-slug>/runs/coordination/lessons/` in the shape of `templates/lesson-record.txt`; genuine means not every run yields a lesson, and a routine run writes none. A failed run is recorded with `status=failure-mode`, never as an `active` lesson. The Reviewer confirms the lesson record exists as part of closeout evidence; a claimed-but-absent record is a false record. An agent-written lesson body carries no command copied from tool output. L9: a defect discovered after a run has closed is a new lane on `main`, not a repair of the closed run. When the project has a backlog file, closeout names the task-record write (`tasks-axi`) beside the ledger row. A change is not landed where it runs by being merged: when the delivery changed an artifact the repository installs outside the checkout — a skill, hook, agent profile, script, or config the runtime loads from its own path — acceptance requires one of two, recorded either way: the installed copy is at the accepted head and a deploy row is appended for it, or the record states the artifact has no installed copy. `scripts/deploy_skill.py` performs the tracked-tree install, per-file hash comparison, and deploy ledger row in one invocation, so the install and its row cannot be separated. Deploy is a gated act: a Lead without a standing waiver routes the deploy gate and the run pauses there, `needs-human-gate` rather than accepted. The obligation is dischargeable from every posture — deploy under a waiver, record that nothing is installed, or route the gate. Derive the answer rather than recalling it, with the doctrine-hash comparison (`relaunch.md`) pointed at whatever this delivery changed: enumerate the artifact's tracked files with `git ls-tree`, hash each installed file with `git hash-object`, and compare each against `git rev-parse "${head}:<path>"`, braced so the shell cannot read the `:` as a history modifier.

Close only panes, tabs, workspaces, and agents created by this run. The caller's checkout is never removed — and never moved: no checkout of another branch, reset, rebase, or clean as part of closeout. Leave it on the branch and head the record names. Cleanup is safe only when: no process runs in any pane this run created; no unexplained tracked change remains (every partitioned Engineer's work committed or its remaining diff explained, and a solo-Lead's remaining diff explained); required reports and artifacts are preserved; no pending Human gate or dependent work remains. As part of the same closeout, consolidate the run's own workspace artifacts under `~/.herdr/projects/<project-slug>/runs/<issue-id>/` so nothing is left loose at the root, retaining the artifacts doctrine requires preserved, including any durable copy of the handoff block, the Reviewer transcript, and any ledger-cited acceptance artifact. Removing anything as redundant follows the by-content proof below, never a name or label. Before deleting any artifact the run created, prove its redundancy by content at a retained location: for a run-created branch already landed on the target line, verify every commit it carries is contained in the pushed target and the branch is reachable from that target — `git rev-list <branch> --not <target-line>` must be empty and the branch must be an ancestor of `origin/<target-line>`; for a file claimed redundant to a retained file, verify identical content by comparing `git hash-object` results or equal `git cat-file` output. This applies only to artifacts the run created and does not alter the rule that the caller's checkout is never removed or moved.

For a project whose root predates this rule and still holds loose per-run files, the project's Lead applies this cleanup at its next closeout, not as a separate pass: move each such file into `runs/<issue-id>/`, move a file attributable to no single issue and not byte-redundant to a retained record into the reserved `runs/coordination/` bucket, or remove it only after proving by content it is redundant to a retained record. The enumerated coordination set and `gates.legacy.md` stay at the root; the sweep never moves or deletes `config.md` or the live coordination files — the ledger, notebook, mailbox, and context pack. Where the sweep moves loose files the context pack cites by path, the same closeout rewrites the pack's references to their new locations so the pack keeps resolving — a Lead-owned pack write, not a move or deletion of the pack. Take the final porcelain re-derivation of the `no unexplained tracked change remains` check as the last act before handoff, after every write closeout performs, including a write by `tasks-axi`, `gh-axi`, or another tool invoked with a repo-writing flag. Leave user-owned or pre-existing resources untouched; if a created resource remains open, state the concrete reason.

**Per-issue agent teardown.** Each delivery is one issue and created its own agents — in partitioned mode one Engineer per scope plus a Reviewer and any Architect a council opened, in solo-Lead mode no Engineer plus a Reviewer and any Architect — recorded in the run context by name, kind, pane, and owned paths. When the issue is accepted or otherwise closed, tear down the agents this run staffed before the flight slot moves to the next issue, tied to the same closeout under the same safe-cleanup preconditions. An agent is torn down by closing the pane this run created to host it (the name clears when the agent exits or its pane closes; `herdr-cli.md` owns the mechanic). Preserve the agent's final evidence report before closing its pane, since the transcript dies with the pane; for a Reviewer, preserve the transcript too (`herdr agent read <name>` into the workspace record), because the verdict names what was found and only the transcript shows what was tried. A pane the Supervisor opened as the Human's hands to host a seat this run staffed counts as created by this run and is torn down with the seat. Never close the caller's own pane or the agent occupying it, never close the Supervisor's own pane (Human-staffed, outliving the delivery), never close a pane an agent shares with unrelated work this run did not create, and do not use `pane release-agent` as teardown — it is a detection-plane report. If an agent is still working, blocked on a Human gate, or holds dependent work another open issue needs, leave it open and state the concrete reason.

**Final handoff.** Write the handoff block in the shape of `templates/final-handoff.txt`, preserving the run's falsifiable prediction and, when determinable within the run, its outcome as `confirmed`, `falsified`, or `pending-next-run` alongside the other acceptance facts. A doctrine-changing run must carry a prediction naming an observable eval id or named anti-pattern; the `none` value remains valid when the run changes no doctrine. Then notify the Human once — `herdr notification show "Delivery <project-slug>: <STATUS>" --body "<OUTCOME>" --sound done` — and send the Supervisor the attention event when one is recorded. The block is the deliverable; the notification only says it exists.
