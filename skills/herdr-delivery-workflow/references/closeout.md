# Closeout

## Acceptance custody

Before review, recompute the implementation repository's full `git rev-parse HEAD`, merge-base, changed-file list, `git --no-optional-locks status --porcelain --untracked-files=all`, and every acceptance command and real exit code. A moving branch, missing commit, stale report, unexplained dirty state, or a staffed Engineer still working is not reviewable: return it to the owning Engineer in partitioned mode, repair the declared scope in solo-Lead mode, or route the blocker. Accept only after an independent Reviewer returns `PASS` for that exact head and the Lead confirms the checkout did not move or become dirty during the review; any implementation change after review creates a new head and requires a fresh review. Preserve one verification ledger for the whole run (`templates/ledger.txt`), repeating the `HEAD` section for every head — the candidate, each repair head, the reviewed head, the integrated head — so each carries its own fresh evidence and verdict. A head with no `Verdict` line has not been reviewed; a repair head that inherits the section above it has not been evidenced. A later green result never silently replaces unreconciled evidence: state what changed and why the earlier failure is resolved. `repair-<n>` numbers the repair cycles from 1 and is a count/label, not a permission: whether another cycle is allowed is decided by the finding-recurrence gate `lead.md` owns ("Flight slot and sequencing"), mechanized by `gate_row.py`, never by this number. A repair head written after a `kind=repair-cap-gate` requires the Human authorization that gate routed, recorded in the gate ledger.

**Acceptance and cleanup.** Before final acceptance, reconcile every `OWED` CI check recorded for a push or merge exactly once by ID with one command before the final handoff/closeout; no `OWED` check may remain unreconciled. A `RED` result is the Lead's red-CI attention event and a finding that must be resolved before closing. Preserve the implementation report, exact reviewed head, Reviewer verdict, integrated head when integration happened, changed files, check results on both the reviewed and integrated head, skipped-check reasons, a causal classification of every failure, residual risks, and next action. For a slice shipping or changing a doctrine-enforcing lint/validator, acceptance custody preserves the output of its real governed-project run as evidence. Acceptance requires claim-shaped checks plus `PASS` for the same exact head; a later green result does not replace an unreconciled earlier failure. On a run that passed independent review and landed (merged, or vacuously-green where there is no CI), the Lead writes one lesson record per genuine lesson learned into `~/.herdr/projects/<project-slug>/runs/coordination/lessons/` in the shape of `templates/lesson-record.txt`; genuine means not every run yields a lesson, and a routine run writes none. A failed run is recorded with `status=failure-mode`, never as an `active` lesson. The handoff's `LESSONS:` line names each record by its store path, written only after reading that record back from the store, or `none`; a claimed-but-absent record is a false record. An agent-written lesson body carries no command copied from tool output. Doctrine adoption follows `lead.md`, "External-signal rule" and "R1 evidence boundaries"; recording a lesson is not adoption. To keep the live store from unbounded growth and drift, the same closeout that writes a lesson record then runs `scripts/lesson_flags.py --project <project-slug>` as a concrete step — triggered by that write, never on a schedule or as a recurring janitor — printing superseded and stale low-use records as retire candidates grouped by status for Human review; the store is bounded by retiring confirmed-obsolete candidates only after the check-before-delete by-content redundancy proof this closeout already applies, and `lesson_flags.py` stays read-only and never deletes or edits a record itself. Malformed lessons are printed as `malformed: <path>: <reason>` and make the `scripts/lesson_flags.py` command exit 1. A closeout that writes no lesson record does not grow the store and runs no survey. Likewise, a closeout whose slice changed `references/RATIONALE.md` runs `scripts/lesson_flags.py --rationale` once, triggered by that change and never on a schedule, and puts its output in the handoff for Human review; it exits 1 on an entry with a missing or malformed provenance tag. A defect discovered after a run has closed is a new lane on `main`, not a repair of the closed run. When the project has a backlog file, closeout names the task-record write (`tasks-axi`) beside the ledger row. A change is not landed where it runs by being merged: when the delivery changed an artifact the repository installs outside the checkout — a skill, hook, agent profile, script, or config the runtime loads from its own path — acceptance requires one of two, recorded either way: the installed copy is at the accepted head or a later reviewed head containing it, with a deploy row appended for that head, or the record states the artifact has no installed copy. `scripts/deploy_skill.py` stages tracked skill files from the accepted head, installs them through `skills add -g`, verifies the installed hashes and modes, and appends the deploy ledger row, including resolving an open deploy-gate via `--resolves`, in one invocation, so the install and its row cannot be separated. Deploy is a gated act: a Lead without a standing waiver routes the deploy gate and the run's outcome is `needs-human-gate`, not accepted; when the install is the only step left, it is the closed delivery's OWED write, carried by its OPEN `kind=deploy-gate` row and mailbox `ATTENTION` wake, like the owed push. The obligation is dischargeable from every posture — deploy under a waiver, record that nothing is installed, or route the gate. Derive the answer rather than recalling it, using the doctrine-hash checklist in `relaunch.md`.

Close only panes, tabs, workspaces, and agents created by this run. Remove any archive sandbox this run created for an env-isolated check (`lead.md`, "Ownership and topology") — a throwaway extraction outside version control, removed without a by-content proof; a dependency directory it symlinks in is left intact, since removing the sandbox directory deletes only the link. The caller's checkout is never removed — and never moved: no checkout of another branch, reset, rebase, or clean as part of closeout. Leave it on the branch and head the record names. Cleanup is safe only when: no process runs in any pane this run created; no unexplained tracked change remains (every partitioned Engineer's work committed or its remaining diff explained, and a solo-Lead's remaining diff explained); required reports and artifacts are preserved; no pending Human gate or dependent work remains. The exception for a delivery's only remaining step is a classifier-gated public push or a Human-owned install: its OWED write is carried by the OPEN `kind=push-gate` or `kind=deploy-gate` row, respectively, and a matching mailbox `ATTENTION` wake (`lead.md`, "Flight slot and sequencing"). Neither gate holds cleanup or the per-issue teardown below; the Reviewer already returned its verdict, and the owed write remains for its owner to discharge, so this exception does not hold the flight slot. As part of the same closeout, consolidate the run's own workspace artifacts under `~/.herdr/projects/<project-slug>/runs/<issue-id>/` so nothing is left loose at the root, retaining the artifacts doctrine requires preserved, including any durable copy of the handoff block, the Reviewer transcript, and any ledger-cited acceptance artifact. Removing anything as redundant follows the by-content proof below, never a name or label. Before deleting any artifact the run created, prove its redundancy by content at a retained location: for a run-created branch already landed on the target line, verify every commit it carries is contained in the pushed target and the branch is reachable from that target — `git rev-list <branch> --not <target-line>` must be empty and the branch must be an ancestor of `origin/<target-line>`; for a file claimed redundant to a retained file, verify identical content by comparing `git hash-object` results or equal `git cat-file` output. This applies only to artifacts the run created and does not alter the rule that the caller's checkout is never removed or moved.

For project-root cleanup, use the coordination-file set and artifact placement rules in `lead.md`, "Durable coordination records". At closeout, move loose per-run files under `runs/<issue-id>/`, and unrelated durable records under `runs/coordination/`; remove a file only after proving it redundant by content. Never move or delete `config.md` or live coordination files. Where the sweep moves loose files the context pack cites by path, the same closeout rewrites the pack's references to their new locations so the pack keeps resolving — a Lead-owned pack write, not a move or deletion of the pack. Take the final porcelain re-derivation of the `no unexplained tracked change remains` check as the last act before handoff, after every write closeout performs, including a write by `tasks-axi`, `gh-axi`, or another tool invoked with a repo-writing flag. Leave user-owned or pre-existing resources untouched; if a created resource remains open, state the concrete reason.

**Per-issue agent teardown.** Before the flight slot moves, close the run-created Peer panes under the custody and evidence rules in `herdr-cli.md`, "Tear down an agent". Leave an agent open only when it is still working, blocked on a Human gate, or holds dependent work, and state the reason. Then run `scripts/closeout_check.py --staffing <run-staffing-record>`; its recorded-pane checks and failure conditions are defined by `templates/staffing-closeout.json` and the checker.

**Final handoff.** Write the handoff block in the shape of `templates/final-handoff.txt`, preserving the run's falsifiable prediction and, when determinable within the run, its outcome as `confirmed`, `falsified`, or `pending-next-run` alongside the other acceptance facts. The prediction field follows `lead.md`, "Repository guidance". Append one `kind=handoff status=recorded:handoff` row through `scripts/gate_row.py` naming the accepted head, so the termination is a first-class ledger event a later relaunch or Supervisor sweep can see, rather than an untracked block; the row's `note=` carries the outcome and the row id goes in the handoff block's HANDOFF field. Then notify the Human once — `herdr notification show "Delivery <project-slug>: <STATUS>" --body "<OUTCOME>" --sound done` — and send the Supervisor the attention event when one is recorded. The block is the deliverable; the notification only says it exists.
