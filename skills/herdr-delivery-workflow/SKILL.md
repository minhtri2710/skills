# Herdr Delivery Workflow

This skill owns Herdr control and bounded delivery inside it: pane and agent mechanics, delivery routing, ownership, evidence, review, Human gates, supervision, and closeout. The installed binary stays the authority for command syntax.

## 1. Preflight and route

Before any Herdr inspection or control command, verify the caller is inside Herdr:

```bash
test "${HERDR_ENV:-}" = 1
```

If the check fails, state that the agent is not running inside Herdr and stop. Do not inspect or control another Herdr session from outside it.

Read `references/herdr-cli.md` before the first control command in any route. It owns preflight, discovery, IDs and caller context, pane and agent mechanics, lifecycle states, seat naming, report-by-prompt, Human notification, read sources, and pane safety. Keep the coordination record in the current run context; do not create shadow state or a second control plane. The durable files this workflow touches live under `~/.herdr/projects/<project-slug>/` (slug derived in `references/project-config.md`): the append-only Human-gate ledger the Lead writes (`references/human-gates-and-closeout.md`), the append-only Supervisor notebook (`references/supervisor-policy.md`), and the Human-owned project config the Lead reads (`references/project-config.md`). A delivery or review-only route reads the project config before staffing, and when it is absent asks the Human whether to create one rather than silently defaulting; the lightweight and supervise routes do not.

Use local tools conditionally and name them in the charter when the outcome needs them: `qmd` for an indexed local Markdown knowledge base, `mcporter` for discovering or calling MCP servers and tools, and the applicable Obsidian tool when the task explicitly concerns Obsidian. If a required tool is unavailable, record degraded mode, use a bounded alternative, and never claim a tool was used when it was not.

Choose the smallest route:

- **Lightweight:** one command, one pane, read-only inspection, or one bounded prompt to an existing agent. Handle it directly with `references/herdr-cli.md` and stop there. Do not read the delivery policies or create a Reviewer, a second Lead, or a recurring watch.
- **Review-only:** a named commit or exact head needs independent review without implementation. Name your own seat first as `references/herdr-cli.md`, "Name a seat", describes, so the verdict has a prompt target; then read `references/peer-policy.md`, staff one Reviewer Peer, and do not create an Engineer or any other writer.
- **Delivery:** a source change needs bounded ownership, one or more Engineers, implementation-to-review handoff, or explicit bounded monitoring/closeout. Read `references/intake-policy.md` first, then `references/lead-policy.md`, before mutation.
- **Supervise:** the Human asks this agent to watch a delivery or a project rather than run it. Read `references/supervisor-policy.md`; take the `supervisor` seat, observe, advise the Lead only, and never staff, edit, commit, or accept.

When a delivery route staffs any Peer — Engineer, Reviewer, or Architect — read `references/peer-policy.md` before sending its charter. When a Human gate appears or resources are ready for cleanup, read `references/human-gates-and-closeout.md`. When architecture, ownership, lifecycle, scalability, latency, compatibility, or proof quality is materially uncertain, read `references/structural-misfit-policy.md` and use its lenses selectively.

Do not add delivery ceremony to a genuinely lightweight task. Escalate when ambiguity changes material scope, safety, external effects, credentials, permissions, security, or an irreversible decision.

## 2. Roles

| Seat | Who staffs it | Decides | Never |
|------|---------------|---------|-------|
| Human | — | gates: push, PR mutation, merge, deploy, irreversible or security-sensitive change, any approval dialog | — |
| Supervisor (`supervisor`) | Human, in its own pane | nothing in the delivery; observes, questions the Lead, relays Human decisions, keeps the notebook | instruct a Peer, edit, commit, answer a gate, accept |
| Lead (`lead-<project-slug>`) | the caller's own seat | intake lane, partition, every commit on the tree, routing of every message and finding, acceptance | write source content, run a second Lead, poll |
| Peer — Engineer | Lead, one per scope | local implementation inside its owned paths | edit outside owned paths, run a writing git command, commit, orchestrate |
| Peer — Reviewer | Lead, on a different kind | `PASS` / `FAIL` / `BLOCKED` on one exact SHA | write anything, review a moving tree |
| Peer — Architect | Lead, only for a `COUNCIL_REQUEST` | one sealed `Assessment` | edit, route, accept |

One Peer profile carries all three dispositions; the charter's `Disposition:` line decides which one this Peer is. Keep the decisions separate: a settled Peer is evidence for the Lead's next step, never acceptance, and a Supervisor message is advice or a relayed Human decision, never a ruling.

Authority is layered, and the layers only tighten: runtime safety, then this skill's role policies, then the project config, then the charter. A charter, a config key, or a Supervisor message can add a constraint; none can move a decision from one seat to another, remove a gate, or authorize an external write. Each seat reads its own layer: the Lead reads this skill and the project config and writes the charters from them; a Peer reads only its charter and the repository, never the Lead's layer. Only a message from the Human is a Human decision — a denied tool call, a harness or classifier refusal, an approval dialog, or a policy inference is never one, and no seat presents it as one (`references/human-gates-and-closeout.md`, "Attribution").

## 3. Run the delivery sequence

A delivery is one issue on one branch in one checkout. The Lead analyzes the issue, partitions it into one or more path-owned scopes, staffs one Engineer per scope, lets them work in parallel on the shared tree, and is the only party that commits. Review happens once, on the quiet head the Lead committed. On a `FAIL` the loop repairs and reviews again. Follow this order:

1. **Intake:** read `references/intake-policy.md`; name the Lead seat, look up the Supervisor seat once, and record the lane, reason, owners, plan, validation, acceptance boundary, exclusions, target repository/product line, base, dependencies, Human gates, applied project-config keys or `Config: none`, and resources created by this run.
2. **Topology:** preserve the caller's focus and working directory. The delivery runs in the caller's existing checkout: one branch, no second working tree, one delivery in flight per project. Parallelism exists only inside one issue, through the partition; a second issue waits for the flight slot. The Lead owns every git write on the tree.
3. **Partition:** analyze the issue against the code before staffing anyone and record the partition (`references/intake-policy.md`, "Partition"): one scope is the base case, several scopes only when their owned paths are disjoint and no scope changes an existing contract another scope consumes; a contract that does not exist yet may be pinned in both charters so producer and consumer run in parallel. Shared paths belong to no Engineer.
4. **Charter:** send each Engineer a charter whose ownership boundary is binding and whose solution shape is provisional (`references/peer-policy.md`): disposition, the recorded lane, plan reference, governing contracts, validation claims, checkout, branch, base, merge-base, its owned paths, the peer scopes and their paths, the shared paths, scoped verification commands, the Lead's seat name, and the report format. The charter is self-contained: everything the Peer needs is in it, and it never points the Peer at this skill's references or the project config. When you staff the Peer, pre-arm its permission posture through the kind's native arguments after `--` on `herdr agent start` and record the posture beside its kind (`references/peer-policy.md`, "Permission posture"): allowlist exactly the read-only and verify commands the charter names plus the report prompt when the kind offers an allowlist; pass a blanket skip only when the kind offers nothing finer and the project config records it (`engineer-args`), as residual risk under the Human's waiver; record `none` when the kind has no permission model, and `prompting` when your own runtime refuses to pass the arguments — start the Peer without them, because that refusal is not a Human ruling. A routine command approval is friction pre-armed here, not a Human gate. Never pre-authorize mutation: push, PR mutation, merge, and deploy stay Human gates.
5. **Execute:** run the Engineers in parallel, each in its own pane, foreground and bounded. Then end the turn as section 4 describes: Peers report by prompt, and each report wakes the Lead.
6. **Quiesce and commit:** when every Engineer is idle, confirm HEAD, branch, and stash list are unchanged since the last record, confirm `git --no-optional-locks status --porcelain --untracked-files=all` is confined to the owned paths and that each scope's entries match what its owner reported as edited, read each scope's diff for an ownership or policy breach — custody, not repair; a bypassed Engineer had no runtime boundary, so the Lead's eyes are the boundary — then stage each scope by its owned paths, commit, and record the candidate head. Nothing unexplained may be committed, whether it sits outside every partition or inside a scope that did not claim it.
7. **Evidence:** run the full acceptance checks on that quiet head and record the exact SHA, merge-base, changed files, porcelain, and every exit code. This is the only implementation evidence that counts; the Engineers' own check results are advisory.
8. **Review:** obtain an independent verdict on the exact candidate head from a Reviewer Peer, in the same checkout with every Engineer idle and the tree quiet at that head. A settled agent state is not acceptance. Staff the Reviewer the same way you staff an Engineer, with `reviewer-args` and the same posture record; write authority stays withheld where the kind allows it, and a Reviewer running bypassed has its no-mutation contract enforced only by charter and by the tree comparison before and after the verdict, which the record names as residual risk.
9. **Repair:** route each in-scope finding to the Engineer that owns the affected paths; a finding that spans partitions or lands outside every partition becomes one sequential slice or `REOPEN_REQUEST`, never a parallel repair. Every resulting head needs fresh evidence and fresh review. The loop is bounded: when the repair cap (default two cycles, `repair-cap` in the project config) is reached without a `PASS`, stop, classify each finding as recurring or new, and route the Human gate or `REOPEN_REQUEST` instead of another cycle.
10. **Integrate:** integration is conditional, not automatic. Do it only when intake recorded a target product line and the Human has not withheld landing; a request that says to stop at review, not to merge, or to leave the branch alone removes this step. When it applies, land the reviewed head onto that line after `PASS`, recompute the integrated head, and rerun the acceptance checks there; the reviewed head and the integrated head stay distinct in the record. When it does not apply, stop at the reviewed head and hand it off as the deliverable.
11. **Gate and close:** stop for Human-owned decisions, including push, PR mutation, merge, and deploy, and notify the Human when a gate opens; accept only after claim-shaped checks and exact-head review; write the final handoff and notify the Human once more; close only resources created by this run when cleanup is safe, including tearing down every Peer before the flight slot moves to the next issue. The Supervisor's pane is never closed by a delivery.

If evidence increases the intake lane or crosses the recorded boundary, stop and route `REOPEN_REQUEST` before continuing.

## 4. Communicate and report

Every channel is named, and every message has one direction:

- **Lead to Peer:** the charter and every later bounded instruction go by `herdr agent prompt <peer-name>`.
- **Peer to Lead:** every report, verdict, `Assessment`, or protocol message — `REOPEN_REQUEST`, `DEPENDENCY_REQUEST`, `BLOCKED`, `COUNCIL_REQUEST` — is printed in the Peer's pane and then sent with `herdr agent prompt lead-<project-slug>` without `--wait`. The prompt is the wake and the payload; the pane is the record. Peers never message each other, the Supervisor, or the Human.
- **Lead to Supervisor:** attention events only — a gate opened, a `REOPEN_REQUEST`, a `BLOCKED` routed upward, the repair cap reached, a transient API/runtime error kills the Lead's turn, a seat compaction or relaunch, the final handoff — by `herdr agent prompt supervisor`, and only when the seat was recorded at intake.
- **Supervisor to Lead:** questions, observations, and relayed Human decisions by prompt; nothing to a Peer.
- **Lead to Human:** the gate record with its ledger line and the final handoff block in the Lead's pane, announced with `herdr notification show` — `--sound request` for a gate, a product fork that needs the Human, or a Peer standing at a routine approval only the Human can clear; one `--sound done` per merge under a standing waiver; and one separate `--sound done` for the handoff; and, on every turn that ends with reports outstanding, one printed line `Awaiting reports: <peer names>` that the Human compares against Herdr's pane labels.

After every dispatch, and after every wake, the Lead ends its turn; it does not block on a Peer, sleep, poll `herdr agent list`, or run a standing watch. Each Peer report is a prompt that wakes the Lead: mid-turn it is handled in that turn, idle it opens a new one. Before ending any turn, the Lead runs `herdr agent list` once and reconciles it with the reports received: an `idle` or `done` Peer with no report is read from its pane with `herdr agent read`; a `blocked` Peer could not report, so inspect with `herdr agent get` and `herdr agent read --source visible`: a routine approval for a command its charter named is a pre-arm miss the Human clears, announced once with `herdr notification show --sound request` and not entered in the gate ledger, while any other dialog is a Human gate; never guess an answer to either; a Peer missing from the list died and is restaffed once — a second death of the same seat on the same head is `BLOCKED` to the Human, not a third launch. The turn then ends with `Awaiting reports: <peer names>` when any report is still owed. Ending a turn is not closing the run: nothing is committed, reviewed, or handed off while an Engineer's report is outstanding. A Peer that goes silent while no other event arrives is caught by the Human, who compares that line with Herdr's pane labels and toasts, not by the Lead. If output is trapped on an alternate screen, use the bounded fallback in `references/herdr-cli.md`: ask for a complete Markdown report in a temporary location and read it directly.

Require every Engineer's evidence report and the Lead's own quiet-head evidence before review, and the Reviewer's verdict before acceptance. A recurring watch is outside this workflow: if monitoring is requested, answer that reports arrive by prompt and the Human watches Herdr's pane labels and toasts, and never create a wait loop, an unbounded retry, or a background watch.
